# Seed validation — LibKa0s

The seed-validation contract `/dev-copilot:validate-seeds LibKa0s <flavor>` runs. The command
supplies the loop (clean tree, one date, status, derive, rule, apply, gate, hand-back) and its
standing rules. This file supplies the library's procedure: the tool, the files it writes, the
precedent a ruling follows and the nuances of each client. The headings below are the interface the
command reads, so keep their names.

LibKa0s ships no per-client id list of its own. What it carries that mirrors a source it does not
own is the kit's client name sets and the payload's assumptions about each client:

- `testkit/client_globals_live.lua` and `testkit/client_globals_forever.lua`, the global function
  names and `C_Name.Member` pairs that the missing-globals gate (`tests/_kit/test_client_globals.lua`)
  reads in every consumer. They are generated by `tools/client_globals_data.lua` from
  [Ketho/BlizzardInterfaceResources](https://github.com/Ketho/BlizzardInterfaceResources), branches
  `live` and `forever`, at the commit sha each file records. The forever file is stored as its
  difference from live.
- The assumptions the shipped payload (`LibKa0s/*.lua`) makes: every `Enum.X.Y` member it reads
  (through an alias such as `local R = Enum.GameRule` too), every `C_X.Y` it names and every bare
  global it calls that some client or kit file knows.

A flavor's **build** is the branch's commit sha. Each run ends in a frozen bundle under
`docs/seed-research/<date>-<flavor>/`. The tool is `tools/seeds/libseeds.py`, and its docstring is
the reference for every candidate and flag kind. The first runs are
`docs/seed-research/2026-11-25-retail/` and `docs/seed-research/2026-11-25-forever/` (LibKa0s#93).

The command's WoW overlay treats a library as `kind=library`: its `gate` section applies, and
`flavor` follows the generic spec, because the roster lists no clients for a library. Neither flavor
reads wago.tools or ForeverDB: Ketho's branches are the source, so there is no `--build` product and
no `Evidence: ForeverDB`.

## Flavors

| Flavor | Source | Seed files | Tools |
| --- | --- | --- | --- |
| `retail` | Ketho/BlizzardInterfaceResources branch `live` (`Resources/GlobalAPI.lua`, `FrameXML.lua`, `LuaEnum.lua`) | `testkit/client_globals_live.lua` (generated; `apply` writes it, and its `tests/_kit/` copy), plus the payload's assumptions (checked only) | `tools/seeds/libseeds.py`, `tools/client_globals_data.lua` |
| `forever` | Ketho/BlizzardInterfaceResources branch `forever` (the same three files) | `testkit/client_globals_forever.lua` (generated, stored against live; `apply` writes it, and its `tests/_kit/` copy), plus the payload's assumptions (checked only) | `tools/seeds/libseeds.py`, `tools/client_globals_data.lua` |

## Rules

- **Only `apply` writes a name set**, and only through `tools/client_globals_data.lua`, after the
  flavor's `regen:<branch>` candidate is ruled accept. Never edit `testkit/client_globals_*.lua` by
  hand. `apply` writes the `tests/_kit/` copy in the same run, so the kit-sync gate stays green.
- **A changed name set is a kit revision.** The run that applies one bumps `Kit.VERSION` in
  `testkit/framework.lua` (and its copy), writes `docs/api/testkit/version-<n>-docs.md` with the
  delta, and re-pins `tests/test_kit_inventory.lua`. A regeneration that leaves the names alone and
  moves only the sha is still a kit revision, because the file's bytes change.
- **Order.** Run `retail` before `forever` when both have moved: the forever file is stored as its
  difference from the checked-in live file, so the generator reads live first.
- **Rulings are data.** They live in `tools/seeds/retail_rulings.json` and
  `tools/seeds/forever_rulings.json`, written only by `libseeds.py rule`. A ruling is keyed
  `regen:<branch>` for the candidate or `shipped:<kind>:<name>` for a flag, never by sha, and it holds
  until the thing it ruled on stops being proposed.
- **Precedent, in this order, never re-litigated:**
  1. a ruling already in the flavor's rulings file;
  2. the guard at the site. An assumption absent on a client is normally a rung of a feature-detected
     ladder (`clients-§3`: feature detection, never a client check). Read the site; when it is
     guarded, rule `keep` and cite the guard's `file:line`, for example "guarded rung: absent on Retail
     by design, `Compat.lua:394`";
  3. the major's API document under `docs/api/<Major>/`, which says what a member answers when the
     client lacks its source;
  4. the *Documented deviations* register in `CLAUDE.md`.
- **What "accept" means here.** Accept `regen:<branch>` when the diff is understood: every removed
  name has been searched for across the collection's checkouts and no unguarded call of it exists,
  or the run lists the consumers that owe a guard. Reject it, with `needs owner review: <why>`, when
  a removed name is still called.
- **What "fix" means here.** A `shipped:` flag ruled `fix` is an unguarded read of something the
  client lacks: a payload bug. It owes a payload edit, with its own minor bump and test, and `apply`
  refuses while one is raised.
- **Evidence.** The bundle's `raw/*.lua.gz` (the three files at the sha), `SOURCES.md` (the sha, its
  commit date, each file's sha256 and URL), `DIFF.md` (the kit-globals diff, the assumption counts,
  the reach check) and the payload's own source.
- **Privacy.** No player name, realm or GUID goes into a bundle, a ruling or a commit. The tool
  sends the User-Agent `LibKa0s-seed-check`.

## Flavor: retail

### Status

```sh
python3 tools/seeds/libseeds.py status --flavor retail
```

Prints `CURRENT <sha> (<bundle>; kit at <sha>)` when the newest `*-retail` bundle ruled the `live`
head, or `NEW <sha> (...)`. The head comes from `git ls-remote`, with the GitHub API as the fallback;
the kit sha is the one `testkit/client_globals_live.lua` records.

### Freeze and derive

```sh
python3 tools/seeds/libseeds.py freeze --flavor retail --sha <build> --date <date> --bundle docs/seed-research/<date>-retail
python3 tools/seeds/libseeds.py derive --bundle docs/seed-research/<date>-retail
```

`freeze` downloads the three files at the sha into `${XDG_CACHE_HOME:-~/.cache}/ka0s-seeds/ketho/<sha>/`
(outside the checkout, so `luacheck .` never reads them), freezes
them gzipped into the bundle's `raw/` (about 150 KB), reads the commit's date from the GitHub API
(`--sha-date` when it is out of reach) and writes `SOURCES.md`. `derive` reads `raw/` alone and runs
the coverage gate: at least 1000 names, `C_Timer.After` among them, and an `Enum` table in
`LuaEnum.lua`. **If the gate fails, stop**: the reader is wrong, not the data. Report the candidate
and flag counts, the unruled count and the added and removed counts.

### Rule

```sh
python3 tools/seeds/libseeds.py check --bundle docs/seed-research/<date>-retail
python3 tools/seeds/libseeds.py rule --tsv <scratchpad>/rulings.tsv --bundle docs/seed-research/<date>-retail
```

`check` lists every unruled key and exits 1, and must print `OK` after `rule`.

- **Candidate** (`accept` or `reject`): `regen:live`.
- **Flags** (`keep` or `fix`): `enum`, `capi` and `global`. On Retail the expected flags are the
  Forever-only rungs: `Enum.GameRule`'s ruleset members, `C_Traits`' group reads in `Role.lua`,
  `RegionalUniqueNamesEnabled`, and the namespaced `C_SpecializationInfo.GetSpecializationInfoForClassID`
  rung, which falls back to the global.

### Apply

```sh
python3 tools/seeds/libseeds.py report --bundle docs/seed-research/<date>-retail --date <date>
python3 tools/seeds/libseeds.py apply  --bundle docs/seed-research/<date>-retail --date <date>
```

`report` comes before `apply` and writes `RULINGS.md` and `DIFF.md`. `apply` refuses while anything is
unruled or a `fix` is raised. With `regen:live` accepted it runs the generator in a scratch copy and
writes `testkit/client_globals_live.lua` and `tests/_kit/client_globals_live.lua` with CRLF; a second
`apply` changes nothing. After a `live` regeneration, re-run the `forever` flavor too: its file is
stored against live.

### After

- When `apply` wrote a file: the kit revision (see *Rules*), and a check that every consumer's
  `test_client_globals` stays green on the new set (search the removed names across the checkouts).
- Write the bundle's `ANALYSIS.md` by hand, in the 2026-11-25 bundles' shape: what the branch says,
  what was proposed and ruled and why, anything that needs owner review, and what a later run should
  re-check.
- Re-resolve any `file:line` a ruling cites when the payload has moved.

### Stage

`testkit/client_globals_live.lua`, `tests/_kit/client_globals_live.lua`, `tools/seeds/retail_rulings.json`,
`docs/seed-research/<date>-retail`, plus the kit revision's files when a set changed. Commit message:
`Seeds (retail): re-validated against <build> (<date>)`.

## Flavor: forever

### Status

```sh
python3 tools/seeds/libseeds.py status --flavor forever
```

Prints `CURRENT <sha> (...)` or `NEW <sha> (...)`, comparing the `forever` head with the newest
`*-forever` bundle; the kit sha is the one `testkit/client_globals_forever.lua` records.

### Freeze and derive

```sh
python3 tools/seeds/libseeds.py freeze --flavor forever --sha <build> --date <date> --bundle docs/seed-research/<date>-forever
python3 tools/seeds/libseeds.py derive --bundle docs/seed-research/<date>-forever
```

The same gate as Retail. The kit's forever set is read as live plus `added` minus `removed`, so the
diff is against the full set a consumer's gate uses.

### Rule

```sh
python3 tools/seeds/libseeds.py check --bundle docs/seed-research/<date>-forever
python3 tools/seeds/libseeds.py rule --tsv <scratchpad>/rulings.tsv --bundle docs/seed-research/<date>-forever
```

Nuances:

- **Candidate:** `regen:forever`. **Flags:** as for Retail.
- **Ketho's forever set over-reports.** It can list names the client lacks (for example
  `GetSpecialization`, which the kit's forever profile removes; `testkit/client_globals.lua`'s
  header). A name present here is evidence, not proof, that WoW Forever has it, so an assumption
  that is *present* is not a reason to drop a guard.

### Apply

```sh
python3 tools/seeds/libseeds.py report --bundle docs/seed-research/<date>-forever --date <date>
python3 tools/seeds/libseeds.py apply  --bundle docs/seed-research/<date>-forever --date <date>
```

As for Retail: `report` first, then `apply`, which writes `testkit/client_globals_forever.lua` and its
`tests/_kit/` copy.

### After

- As for Retail, with the headless suite run under both kit profiles.
- Write the bundle's `ANALYSIS.md` by hand, in the 2026-11-25 bundles' shape.

### Stage

`testkit/client_globals_forever.lua`, `tests/_kit/client_globals_forever.lua`,
`tools/seeds/forever_rulings.json`, `docs/seed-research/<date>-forever`, plus the kit revision's files
when a set changed. Commit message: `Seeds (forever): re-validated against <build> (<date>)`.

## Gate

```sh
lua tests/run.lua
KA0S_KIT_CLIENT=forever lua tests/run.lua
~/.claude/dev-copilot/bin/ka0s-bounded luacheck .
python3 -m pytest -q tools/seeds
```

The suite bounds itself (the kit's resource guard), and `luacheck` loads no kit, so it runs bounded
(`testing-§15`). luacheck must report 0 warnings and 0 errors, and every suite 0 failed. Without
pytest, `python3 -m unittest discover -s tools/seeds` runs the same cases.

## Notes

- **The `derive` record is taken before `apply`.** A bundle's `candidates.json` proposes the
  regeneration its run applied, so re-deriving the same bundle after `apply` proposes nothing: the kit
  then records the bundle's sha. That is the expected end state, not a drift.
- **Bundle size.** Each bundle's `raw/` is about 150 KB: the three files, gzipped. The source
  repository declares no license; the files list the client's own API names and enum values, the
  facts the kit's name sets already carry.
- **What the scan cannot see.** The assumption scan is a static read: a name built at run time
  (`_G[name]`), a member read through a local that is not a direct `Enum.X` alias, and a bare call of
  a name no source and no kit file knows (a host's global, an upvalue) are not checked. A false
  negative there costs a missed flag, never a red gate. A cached global (`local GetTime = GetTime`,
  `local X = _G.X`) is checked at its capture, the one place it reads the client; its later calls go
  through the upvalue and are not. A local copied under another name (`local now = GetTime`) is not
  seen at all.
- **No shared helper.** The tool copies the addon seed tools' pattern (the build pin, the cache, the
  bundle, the rulings) and imports nothing across repos; LibKa0s#91, the survey that led to the
  contracts, closed on 2026-11-16 without one.
